# lifelog — 開発コンテキスト

## 概要
ライフログ＋ライフコーチの静的PWA（ビルド不要）。コーデ・食事・サプリ・運動・体重・買い物などをカテゴリ単位で日々記録する。データは`localStorage`のみ（キー`lifelog_v2`）で、バックエンドは無い。

## 構成
- `index.html`：CSS/JSをインラインで持つ本体。`onclick="..."`のインラインハンドラからグローバル関数を呼ぶ構成。
- `logic.js`：DOMに触れない純粋関数。クラシックスクリプト（UMD）で、ブラウザではグローバル`LifeLogLogic`、Nodeでは`require()`で読む。**ESMにしない**（インラインのonclickがグローバルに依存するため）。
- `test/logic.test.mjs`：`npm test`（`node --test`）。`logic.js`を`import logic from '../logic.js'`で読む。
- `sw.js`：`index.html`と`logic.js`はネットワーク優先、それ以外はキャッシュ優先。**`ASSETS`に新しいファイルを足すときは`CACHE`のバージョンも上げる**（古いキャッシュを`activate`で削除する仕組みのため）。

## データ構造
```
state = { cats: [...], logs: { 'YYYY-MM-DD': { <catId>: entry } } }
cat   = { id, name, type, icon, color, items: [string], createdAt,
          groups?: [{ id, name }],            // 「分類を始める」を押したカテゴリのみ
          types?:  { [groupId]: [string] },   // グループ内の種類（任意の小見出し）
          brands?: [{ id, name, short }],       // ブランドの一覧（カテゴリごと）。name=正式名称, short=略称（任意、無ければ ''）
          meta?:   { [名前]: { g, t, s, q, r, b? } } }  // g=グループID/null, t=種類/'', s=夏|冬|通年, q=着数(1〜99), r=手放した, b=ブランドID（未設定なら属性なし）
entry = { v: [string] | string, free, kcal, yen, min, km, steps, wt, fat, note, ts }
```
- **`groups`/`types`/`brands`/`meta`は「今の形に足すだけ」のフィールド**。`items`と`logs`の形は変えない（旧バージョンは追加フィールドを読み飛ばすので、書き出し・取り込みもそのまま動く）。
- 服の管理のロジックは`logic.js`にある：`startGrouping`／`setMeta`／`bulkSetMeta`／`suggestMeta`＋`applyMeta`／`renameItem`／`mergeItems`／`deleteItem`／`countUsage`＋`periodRange`／`pushSnapshot`＋`popSnapshot`／`repairMeta`。
- **名前変更・統合は`renameItem`／`mergeItems`を使う**（`items`・`meta`・過去の`logs`の`v`と`free`を一緒に付け替える）。`items`だけを直接書き換えない。
- 変更先が既存の服と同名（全角・半角・大文字小文字の違いのみを含む）なら、名前変更は`exists`で断り、統合（`mergeItems`）で行う。統合では着数を合算し、同じ日の重複は1回にする。
- **記録のある服は削除できない**（`deleteItem`が`used`を返す）。統計を残すため、手放した扱い（`r: true`）にする。
- 集計期間は`periodRange`：`30d`／`90d`／`6m`（180日）／`1y`（365日）／`all`（制限なし）。今日を含む直近N日で、既存のインサイトの90日と同じ窓。
- 服などの選択項目は**名前の文字列**で`logs`に保存される（IDではない）。項目名を変えるときは過去の`logs`も一緒に書き換えること。
- `v`が配列のカテゴリ（ファッション・サプリ）では、同じ名前を2回入れない（`LifeLogLogic.mergeSelection`／`repairLogs`）。
- 「インポート」は全データの**上書き**。エクスポート後にスマホで付けた記録は、再インポートで失われる。

## 服の管理画面（`view-wardrobe`）
- 設定タブの「整理 → 服の管理」から開く（`nav('wardrobe')`）。下のタブは「設定」が選択中のままで、**画面幅1100px以上では`body.wide-view`で画面を広げ、下のタブを隠して表形式**にする（表に必要な幅は約1030px。列を足す・切り替え幅を下げるときは、列の最小幅の合計も確認すること。1100pxで右端が収まることを確認済み）。スマホ幅では縦のカード。同じDOMをCSSで切り替えている。
- **対象（`LifeLogLogic.wardrobeCategories`）は、①分類を始めたカテゴリ（`cat.groups`あり。種類をあとで変えても、服が空になっても対象のまま）、②種類が「ファッション」で服が1つ以上あるカテゴリ（これから分類を始める候補）**。分類を始めていない食事・サプリなどは対象外（初期のグループが服用のため）。①を外すと、カテゴリ編集画面が服の編集を「服の管理」へ案内するのに、そこから届かなくなる。
- 描画と操作のつなぎは`index.html`の`wd*`関数。**絞り込み・並べ替え・集計は`LifeLogLogic.wardrobeRows`**、変更は`logic.js`の関数（`setMeta`／`bulkSetMeta`／`renameItem`／`mergeItems`／`deleteItem`／`addItem`／`startGrouping`／`suggestMeta`＋`applyMeta`）を呼ぶだけにする。
- **変更は必ず`wdMutate`を通す**：操作の直前の状態を保存し、成功したときだけ確定する。**本体のデータを先に保存し（`wdPersist`）、履歴はそのあと**。本体が入らないときは保存済みの履歴を消して空きを作り、それでも入らなければメモリの変更を取り消して知らせる（メモリと保存データを食い違わせない）。保存先は`localStorage`の`lifelog_v2_undo`（別キー。エクスポートには含まれない）。**10件まで**で、容量が足りないときは古い順に捨てる。取り込み・全消去でクリアする。元に戻すは**全データ**を戻すので、操作のあとに付けた記録があれば確認を出す。
- 名前を既存の服と同じにすると統合の確認を出す。記録のある服は削除ボタンを押せない。
- 「カテゴリを編集」画面は、**分類を使うカテゴリ（`cat.groups`あり）では服の編集を出さず、「服の管理」へ案内する**（そこで名前を直すと過去の記録の名前と食い違うため）。分類を使わないカテゴリは従来どおり。
- 記録画面（`openLog`）は`LifeLogLogic.visibleItems`で、手放した服を隠す（その日にすでに選ばれている服は残す）。インサイトのバリエーション率・おすすめは`activeItems`（現役のみ）が対象。使用回数のグラフには、使った手放した服だけ「手放した」の表示つきで残す。
- 記録の自由記入が、全角・半角・大文字小文字の違いだけでリストの服と同じなら、すでにある服として扱う（似た名前の服が増えない）。新しい名前を足すときは`addItem`を使う（分類を使うカテゴリでは名前から推定した属性が入る）。
- **並べ替えで、グループ・ブランドが未設定の服は、昇順でも降順でも最後**（空の値は常に最後。未設定だけ見たいときは絞り込みを使う）。最終着用日の並べ替えは別で、未着用の服が昇順の先頭に来る（長く着ていない服を探すため）。
- **ブランド**：カテゴリごとの一覧（`cat.brands`、「ブランドの管理」で追加・名前変更・削除）。服には**ブランドID**を付ける（`meta.b`）ので、名前・略称を直しても服は付いたまま。**正式名称は一覧・絞り込みに、略称（任意）は表や選択欄などの狭いところに出す**（`brandText`）。名前・略称は他のブランドと重ならない。使っている服（手放した服を含む）があるブランドは削除できない。グループ・種類とは別の、独立した札（入れ子ではない）。
- **名前からのブランド推定**（`suggestBrands`→確認画面→`applyBrands`）：①登録済みのブランドが名前に含まれていればそのブランド（英字は名前の先頭、日本語はどこか）②辞書（`BRAND_DICTIONARY`。カタカナの表記や、`OCW-`・`MTG-`などの型番）の正式名称③名前の先頭の英字（ハイフン・数字の手前まで）が**同じカテゴリで2つ以上の服に共通**していればその英字。1つだけの服は推定しない。`TK`・`PS`・`UA`のような略称は、どのブランドか断定できないので、そのまま登録して、正式名称は利用者が付ける。服を追加したときも、登録済みのブランドは自動で付く（`addItem`）。
- 起動時・取り込み時に`repairMeta`を通す（ブランドの一覧・服のブランドの不正な値も直す）。
- E2Eは未整備。画面の確認は、Playwrightで合成データを使い、スマホ幅・PC幅・ダークモードで行った（リポジトリには含めていない）。

## 変更時の注意
- ロジック（集計・移行・重複排除など）は`logic.js`に切り出してテストを書く。DOM描画と切り離せる部分を`index.html`に直接書かない。
- 保存済みデータの形を変える場合は、起動時とインポート時の両方で移行・修復を通す（`repairLogs`の呼び出し箇所を参照）。
- テスト追加時は、対象コードを一時的に無効化してテストが落ちることを確認する（偽陽性防止）。

## 開発予定（コーデの整理）
服が増えて選択画面が長くなったことへの対応。この順で進める：
1. 不具合修正（重複記録）— 完了
2. データモデル拡張と「服の管理」画面 → 利用者がPCで既存データを棚卸し
   - 2-a. ロジックとテストのみ（`logic.js`。画面の変更なし）— 完了
   - 2-b. 「服の管理」画面（設定タブの中。スマホは縦のカード、PC幅は表形式。名前変更・統合・一括設定・元に戻す）。選択画面では手放した服を隠す（ただしその日に記録済みの服は残す）— 完了
3. 記録画面（グループ見出し・今の季節・最近着た順・その場で追加）とグループ別の統計

設計の結論：
- **グループ（トップス／ボトムス／アウター）＋種類（長袖T・パーカー・ジャケット等の任意の小見出し）の2段**。グループは部位、種類は品目。両方とも利用者が追加できる。
- 項目は`{名前, グループ, 種類, 季節（夏/冬/通年）, 着数, 状態（現役/手放した）}`を持つ。季節の初期値は名前のキーワードから推定する（着用月からは推定しない。記録期間が1シーズン分しかないため）。
- **手放した服は選択画面から隠すだけで、`logs`・統計には残す**（着回しの統計が目的のため）。バリエーション率とおすすめの対象からは外す。
- 同じような服を複数持つ場合は1項目のまま「着数」で表し、統計では1着あたりの回数も出す。
- 統計はグループごとに分けて出す（Tシャツとパンツを同じランキングに混ぜない）。集計期間は切り替えられ（30日／90日／半年／1年／全期間）、**初期値は全期間**。画面に集計期間を必ず表示する（現在のインサイトの使用回数は直近90日だが、その表示が無く全期間の数字に見える）。
- 時計・ネックレス・シューズなど数の少ないカテゴリは、分類を始めず平らな一覧のまま使う。分類を使うかどうかはカテゴリごとに選ぶ。
- 棚卸しの操作は、直前の状態を自動で保存して「元に戻す」を付ける（取り込みが全データの上書きで、操作が連続するため）。
