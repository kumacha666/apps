# lifelog — 開発コンテキスト

## 概要
ライフログ＋ライフコーチの静的PWA（ビルド不要）。コーデ・食事・サプリ・運動・体重・買い物などをカテゴリ単位で日々記録する。データは`localStorage`のみ（キー`lifelog_v2`）で、バックエンドは無い。

## 構成
- `index.html`：CSS/JSをインラインで持つ本体。`onclick="..."`のインラインハンドラからグローバル関数を呼ぶ構成。
- `logic.js`：DOMに触れない純粋関数。クラシックスクリプト（UMD）で、ブラウザではグローバル`LifeLogLogic`、Nodeでは`require()`で読む。**ESMにしない**（インラインのonclickがグローバルに依存するため）。
- `test/logic.test.mjs`：`npm test`（`node --test`）。`logic.js`を`import logic from '../logic.js'`で読む。
- `sw.js`：`index.html`と`logic.js`はネットワーク優先、それ以外はキャッシュ優先。**`ASSETS`に新しいファイルを足すときは`CACHE`のバージョンも上げる**（古いキャッシュを`activate`で削除する仕組みのため）。
- **`index.html`と`logic.js`の新旧の食い違いを防ぐ仕組み**：公開サーバー（GitHub Pages）は`Cache-Control: max-age=600`（10分）で配信するため、**更新の直後は「新しい`index.html`＋古い`logic.js`」になることがある**（画面の一部が描画されず、空になる。#530の直後に実際に起きた）。対策は2つ。①`sw.js`のネットワーク優先の取得は`cache: 'no-cache'`で、毎回サーバーに確認する（変更が無ければ304）。②`index.html`は起動時に`LifeLogLogic.VERSION`を`LOGIC_VERSION_EXPECTED`と突き合わせ、合わなければ**一度だけ**キャッシュを避けて取り直して再読み込みし、それでも合わなければ画面で知らせる（無限に再読み込みしない。記録には触れない）。
  - **`logic.js`の公開する関数や戻り値の形を変えたら、`VERSION`を上げる**。`index.html`の`LOGIC_VERSION_EXPECTED`を同じ値にし、`test/api-v<新しい版>.json`（`Object.keys(LifeLogLogic).sort()`の一覧）を足す。`npm test`が、①2つの値の一致、②公開する関数の一覧が変わったのに`VERSION`が同じ、を検出する。**戻り値の形だけ変えた場合は一覧が変わらず検出できないので、自分で上げること**（#530で`pickerSections`に`rare`を足したのに版が無かったため、古い`logic.js`との組み合わせで空になった）。
  - 画面の確認でキャッシュを再現するときは、Playwrightの`route()`を使わない（`route()`を使うとChromiumのHTTPキャッシュが無効になる）。手動の再読み込みもキャッシュを無視するので、再現には通常のページ移動（`goto`）を使う。

## データ構造
```
state = { cats: [...], logs: { 'YYYY-MM-DD': { <catId>: entry } } }
cat   = { id, name, type, icon, color, items: [string], createdAt,
          groups?: [{ id, name }],            // 「分類を始める」を押したカテゴリのみ
          types?:  { [groupId]: [string] },   // グループ内の種類（任意の小見出し）
          brands?: [{ id, name, short }],       // ブランドの一覧（カテゴリごと）。name=正式名称, short=略称（任意、無ければ ''）
          meta?:   { [名前]: { g, t, s, q, r, b?, z? } } }  // g=グループID/null, t=種類/'', s=夏|冬|通年, q=着数(1〜99), r=手放した, b=ブランドID（未設定なら属性なし）, z=提案に出さない（trueのときだけ持つ）
entry = { v: [string] | string, free, kcal, yen, min, km, steps, wt, fat, note, ts }
```
- **`groups`/`types`/`brands`/`meta`は「今の形に足すだけ」のフィールド**。`items`と`logs`の形は変えない（旧バージョンは追加フィールドを読み飛ばすので、書き出し・取り込みもそのまま動く）。
- 服の管理のロジックは`logic.js`にある：`startGrouping`／`setMeta`／`bulkSetMeta`／`suggestMeta`＋`applyMeta`／`renameItem`／`mergeItems`／`deleteItem`／`countUsage`＋`periodRange`／`pushSnapshot`＋`popSnapshot`／`repairMeta`。
- **名前変更・統合は`renameItem`／`mergeItems`を使う**（`items`・`meta`・過去の`logs`の`v`と`free`を一緒に付け替える）。`items`だけを直接書き換えない。
- 変更先が既存の服と同名（全角・半角・大文字小文字の違いのみを含む）なら、名前変更は`exists`で断り、統合（`mergeItems`）で行う。統合では着数を合算し、同じ日の重複は1回にする。
- **記録のある服は削除できない**（`deleteItem`が`used`を返す）。統計を残すため、手放した扱い（`r: true`）にする。
- 集計期間は`periodRange`：`30d`／`90d`／`6m`（180日）／`1y`（365日）／`all`（制限なし）。今日を含む直近N日で、既存のインサイトの90日と同じ窓。
- 服などの選択項目は**名前の文字列**で`logs`に保存される（IDではない）。項目名を変えるときは過去の`logs`も一緒に書き換えること。
- `v`が配列のカテゴリ（ファッション・サプリ）では、同じ名前を2回入れない（`LifeLogLogic.mergeSelection`／`repairLogs`）。
- 「インポート」は全データの**上書き**。エクスポート後にスマホで付けた記録は、再インポートで失われる。

## 服の管理画面（`view-wardrobe`）
- 設定タブの「整理 → 服の管理」から開く（`nav('wardrobe')`）。下のタブは「設定」が選択中のままで、**画面幅1100px以上では`body.wide-view`で画面を広げ、下のタブを隠して表形式**にする（表に必要な幅は約1050px。列を足す・切り替え幅を下げるときは、列の最小幅の合計も確認すること。1100pxで右端が収まることを確認済み）。スマホ幅では縦のカード。同じDOMをCSSで切り替えている。
- **対象（`LifeLogLogic.wardrobeCategories`）は、①分類を始めたカテゴリ（`cat.groups`あり。種類をあとで変えても、服が空になっても対象のまま）、②種類が「ファッション」で服が1つ以上あるカテゴリ（これから分類を始める候補）**。分類を始めていない食事・サプリなどは対象外（初期のグループが服用のため）。①を外すと、カテゴリ編集画面が服の編集を「服の管理」へ案内するのに、そこから届かなくなる。
- 描画と操作のつなぎは`index.html`の`wd*`関数。**絞り込み・並べ替え・集計は`LifeLogLogic.wardrobeRows`**、変更は`logic.js`の関数（`setMeta`／`bulkSetMeta`／`renameItem`／`mergeItems`／`deleteItem`／`addItem`／`startGrouping`／`suggestMeta`＋`applyMeta`）を呼ぶだけにする。
- **変更は必ず`wdMutate`を通す**：操作の直前の状態を保存し、成功したときだけ確定する。**本体のデータを先に保存し（`wdPersist`）、履歴はそのあと**。本体が入らないときは保存済みの履歴を消して空きを作り、それでも入らなければメモリの変更を取り消して知らせる（メモリと保存データを食い違わせない）。保存先は`localStorage`の`lifelog_v2_undo`（別キー。エクスポートには含まれない）。**10件まで**で、容量が足りないときは古い順に捨てる。取り込み・全消去でクリアする。元に戻すは**全データ**を戻すので、操作のあとに付けた記録があれば確認を出す。
- 名前を既存の服と同じにすると統合の確認を出す。記録のある服は削除ボタンを押せない。
- **状態は3つ（選択式）：現役／出さない／手放した**。「出さない」（`meta.z`）は、**持っているが、記録画面の上の列・バリエーションの母数・提案に出さない**服（礼服・部屋着・着ない服など）。普通の一覧では選べて、使用回数の統計にも残る（手放した服と違い、記録画面から隠さない）。`r`と`z`の組み合わせは`WD_STATUS`で決める：出さない＝`{r:false, z:true}`、手放した＝`{r:true, z:false}`、現役＝両方外す（zはfalseにすると属性ごと消える）。統合では、全部が「出さない」のときだけ残る。絞り込みの「現役」は出さない服も含む（持っている服）。表の状態の列は96px。
- 「カテゴリを編集」画面は、**分類を使うカテゴリ（`cat.groups`あり）では服の編集を出さず、「服の管理」へ案内する**（そこで名前を直すと過去の記録の名前と食い違うため）。分類を使わないカテゴリは従来どおり。
- 記録画面（`openLog`）は`LifeLogLogic.visibleItems`で、手放した服を隠す（その日にすでに選ばれている服は残す）。インサイトのバリエーション率・おすすめは`activeItems`（現役のみ）が対象。使用回数のグラフには、使った手放した服だけ「手放した」の表示つきで残す。

## 記録画面の服の選択（分類を使うカテゴリ）
- **分類を使うカテゴリ（`cat.groups`あり）だけ**、`openLog`が新しい選択画面（`pk*`関数、状態は`pk`）を出す。分類を使わないカテゴリ（時計・ネックレス等）は従来の平らなチップのまま（`#chip-box`、`toggleChip`）。
- 表示の並び・絞り込みは**`LifeLogLogic.pickerSections`**（DOMに触れない）。画面側は描画とクリックのつなぎだけ。
- 見出しは**グループ→種類**。種類なしの服は「その他」（種類が1つも無いグループでは出さない）。グループ未設定の服は最後の「未分類」。グループ見出しは開閉できる（検索中は全部開く）。
- **季節の切り替え（夏／冬／すべて）の初期値は、記録する日の月で決める**（`defaultSeasonView`）：6〜9月＝夏、11〜3月＝冬、**4・5・10月＝すべて**（急に暑く・寒くなる時期のため、実データで夏の服が10/22まで・冬の服が10/25から着られていたことから決めた）。夏の表示は夏と通年、冬の表示は冬と通年。手で切り替えられる。
- **選択中の服は、季節外でも手放した服でも一覧に残す**。選んだ服は上の「選択トレイ」に常に出て、タップで外せる（トレイが選択の正。保存はここから読む）。**リストに無い名前（過去の記録だけに残っている名前）もトレイに出るので、何も触らずに保存しても記録は失われない**。
- **検索は名前と、ブランドの正式名称・略称**（全角半角・大文字小文字を問わない）。検索中は季節で絞らず全部から探し、上の列（上に出す服）は出さない。手放した服は検索でも出ない（選択中なら残る）。
- **上の列「上に出す服」**：バランスよく着るために、**既定は「着ていない順」**（一度も着ていない服が先頭、次に最後に着た日が古い順。「45日」のように何日前かを出す）。切り替えで「回数が少ない順」（着数で割った1着あたりの回数。同じなら最後に着た日が古い順）と「最近着た順」も選べる。最大8件。
  - **着ていない順・回数が少ない順の対象は、今の季節（と通年）の現役の服。「出さない」服は、選択中でも外す**。数えるのは**記録している日より前の記録だけ**（その日自身と未来の記録は使わない）。検索中は出さない。
  - **上の列の「この列に出さない服を選ぶ…」**で、タップした服を「出さない」にする（✕が付く。モード中のタップは選択にならない）。保存は`wdMutate`を通す（元に戻せる。保存できなければ取り消して知らせる）。服の管理で戻せる。
  - **「最近着た順」**：記録している日の30日前の日から前日まで（その日自身と、それより後の記録は除く）に着た服を新しい順。季節に関係なく出す（季節の切り替えを手で戻さなくて済むように）。**「出さない」服は、この並びからも外す**（8件に絞る前に外すので、除外した分だけ件数が減ることはない。普通の一覧では選べる）。
- **「＋新しい服を追加」**：`LifeLogLogic.addItem`で追加し**すぐ保存**する（キャンセルしても追加した服は残る。不要なら服の管理で削除できる）。**保存は`wdPersist`（本体を先に保存→入らなければ保存済みの履歴を削って再試行）を通し、それでも入らなければメモリの追加を取り消して知らせる**（`save()`を直接呼ばない。メモリだけ追加済みで再起動すると消える状態を作らないため）。追加した服は自動で選択される。同じ名前（全角半角などの違いを含む）の服があれば、新しく作らずそれを選ぶ。
- 自由記入欄は、**以前の記録に服の一覧に無い文字が残っている時だけ**出す（普段は出さない。新しい服は上の追加から）。保存時の扱い（`mergeSelection`、一覧に無い名前の確認）は従来どおり。**選択トレイで外した名前が自由記入欄に同じ文字で残っていれば、一緒に消す**（残すと保存時の`mergeSelection`で選択に戻ってしまう）。
- 保存する`v`は、リストの並び順（リストに無い名前は選んだ順で末尾）。
- **ブランド名は、服のボタンには、どの場所でも必ず出す**（`brandTag`。略称があれば略称、無ければ正式名称、ブランド未設定なら何も出さない）：下の一覧・上の列（着ていない順／回数が少ない順／最近着た順。日数・回数と一緒に）・選んだ服（トレイ）・「出さない服を選ぶ」中・平らな一覧（時計・靴など。ブランドを付けたカテゴリ）。服が多いと、ブランド名が見えないと探せないため（上の列は以前、日数・回数のかわりにブランド名を消していた）。ブランド名は、日数・回数（紫）と見分けられる色・太さで、名前の横に小さく出す（`.pk-brand`）。検索も、ブランドの正式名称・略称に当たる。
- 記録の自由記入が、全角・半角・大文字小文字の違いだけでリストの服と同じなら、すでにある服として扱う（似た名前の服が増えない）。新しい名前を足すときは`addItem`を使う（分類を使うカテゴリでは名前から推定した属性が入る）。
- **並べ替えで、グループ・ブランドが未設定の服は、昇順でも降順でも最後**（空の値は常に最後。未設定だけ見たいときは絞り込みを使う）。最終着用日の並べ替えは別で、未着用の服が昇順の先頭に来る（長く着ていない服を探すため）。
- **ブランド**：カテゴリごとの一覧（`cat.brands`、「ブランドの管理」で追加・名前変更・削除）。服には**ブランドID**を付ける（`meta.b`）ので、名前・略称を直しても服は付いたまま。**正式名称は一覧・絞り込みに、略称（任意）は表や選択欄などの狭いところに出す**（`brandText`）。名前・略称は他のブランドと重ならない。使っている服（手放した服を含む）があるブランドは削除できない。グループ・種類とは別の、独立した札（入れ子ではない）。
- **名前からのブランド推定**（`suggestBrands`→確認画面→`applyBrands`）：①登録済みのブランドが名前に含まれていればそのブランド（英字は名前の先頭、日本語はどこか）②辞書（`BRAND_DICTIONARY`。カタカナの表記や、`OCW-`・`MTG-`などの型番）の正式名称③名前の先頭の英字（ハイフン・数字の手前まで）が**同じカテゴリで2つ以上の服に共通**していればその英字。1つだけの服は推定しない。`TK`・`PS`・`UA`のような略称は、どのブランドか断定できないので、そのまま登録して、正式名称は利用者が付ける。服を追加したときも、登録済みのブランドは自動で付く（`addItem`）。
- 起動時・取り込み時に`repairMeta`を通す（ブランドの一覧・服のブランドの不正な値も直す）。
- E2Eは未整備。画面の確認は、Playwrightで合成データを使い、スマホ幅・PC幅・ダークモードで行った（リポジトリには含めていない）。

## ファッションの統計（インサイト画面）
- 集計は**`LifeLogLogic.fashionStats`**（DOMに触れない）、期間の表示は`periodLabel`。画面（`getInsights`のファッション部分）は描画だけ。
- **集計期間はインサイト画面の上のボタンで切り替える（30日・90日・半年・1年・全期間、初期値は全期間）。選択は`insPeriod`で、ファッションの統計だけに効く**（記録率・直近30日の記録などは変えない）。**画面に集計期間を必ず出す**（📅 集計期間）。以前は直近90日だったのに表示が無く、全期間の数字に見えていた。
- **グループ別**に出す（トップス／ボトムス等。分類を使うカテゴリのみ）。1グループにつき：見出し（現役の点数・着数の合計・期間内の延べ着用回数）・バリエーション・提案・最多・使用回数のグラフ。グループ未設定の服と、一覧に無い名前（記録だけに残る名前。「記録のみ」の印つき）は「未分類」。分類を使わないカテゴリ（時計等）は見出し無しの1つのまとまり。服が無いグループは出さない。
- **手放した服は、その期間に着ていれば統計に残る**（「手放した」の印）。バリエーション・提案・着数の合計・現役の点数には数えない。**「出さない」服は、バリエーションの母数と提案から外す**（統計の一覧・現役の点数・着数の合計には残る）。
- **着数が2以上の服は「2着」の印と、1着あたりの回数（`perPiece`）を出す**。
- **バリエーションと提案は、今の季節（と通年）の現役の服だけが対象**（`defaultSeasonView(今日)`。4・5・10月は「すべて」）。冬に夏の服を「着ていません」と言わないため。**提案（一度も着ていない／14日以上着ていない）は、選んだ期間に関係なく全記録で判定する**（期間を狭めても「最後に着たのが何日前か」は変わらない）。提案は1グループ最大5件で、残りは「ほかN点」。
- **統計を出すかどうかは、そのカテゴリに記録が（いつでも）あるか（`hasLogs`）で決める。現在の服の数には依存させない**（統合後に1点になっても、過去にだけ残る名前を落とさない）。直近30日に記録が無くても、過去の記録があれば「未記録」の警告を残したまま、選んだ期間の統計を続けて出す（半年・1年・全期間のため。この場合は「直近30日の記録回数」の行は出さない）。記録が全く無いカテゴリは従来どおり「未記録」だけ。期間ボタンも、統計を出すカテゴリが1つでもあれば出す。バリエーションだけは、対象が1点では意味が薄いので2点以上のときだけ出す。
- グラフは最初の8件で、「ほかN点を見る」で全部出す（`insMore`）。回数の多い順で、同じ回数は一覧の並び順。
- E2Eは未整備。画面の確認は、Playwrightで合成データと実データを使い、スマホ幅・ダークモードで行った（リポジトリには含めていない）。

## 平らな選択一覧の並び替え（分類を使わないカテゴリ）
- **分類を使わず、選ぶ項目のある、すべてのカテゴリ**（時計・ネックレス・靴・食事・サプリなど。**新しく作ったカテゴリも、設定なしで自動的に**）の記録画面に、選択一覧の上に**「並び」の切り替え（登録順／着ていない順／回数が少ない順）**を出す。条件は「分類を使わない」「項目が2つ以上ある」だけで、カテゴリの種類・名前には依存しない（`openLog`の`flat`、`flat*`関数）。項目が1つだけのカテゴリには出さない。分類を使うカテゴリは、従来の上の列（`pk*`）。
- 並びは**`LifeLogLogic.sortItems`**（DOMに触れない）。**着ていない順**＝一度も着ていない（記録の無い）項目が先頭、次に最後に着た日が古い順。**回数が少ない順**＝着数で割った1着あたりの回数が少ない順（同じなら最後に着た日が古い順）。**「出さない」（`meta.z`）の項目は、どの並びでも最後**。**数えるのは記録している日より前の記録だけ**（その日自身と未来は使わない。過去の日を開いたときは、その日より前の記録で並ぶ）。ボタンには、「45日」「3回」「未着用」（ファッション以外は「記録なし」）を小さく添える（登録順では出さない）。
- **ラベルと既定は種類で変わる**（`sortModes`・`defaultSortMode`）：ファッションは「着ていない順」が既定（バランスよく着たいため）。それ以外（食事・サプリ・運動・買い物など）は「登録順」が既定で、ラベルは「久しぶり順」（決まった並びのほうが選びやすいため）。
- **選んだ並びは、カテゴリごとに覚える**（`localStorage`の`lifelog_sort_v1`。表示の好みで、記録のデータではない。エクスポートには含まれない）。並び替えても、選んだ状態は保たれる。
- **保存する`v`の順は、表示の並びに関係なく、一覧（`cat.items`）の並び順**（`orderByItems`）。表示を並び替えても、過去の記録の並びが変わらないように。

## ホームのカレンダー（日付をタップで開く）
- 履歴タブに行かなくても、**ホームの日付（「11月24日 (火) 📅」）をタップすると、下からカレンダーのシート（`#cal-modal`、`calSheet*`関数、状態は`cal`）が開く**。「あのとき何を着てたっけ」を、ホームから2タップで確認するため。
- シートは、月のカレンダー（日曜はじまり、`LifeLogLogic.monthCells`）と、**日付を選ぶと出るその日の記録のプレビュー**（`LifeLogLogic.dayEntries`＋`entryText`。カテゴリの並び順。服以外も出す）。**選んだだけではホームの日付は変わらない**。「この日を開く」を押すと、その日のホームへ移る（`jumpToDate`）。「閉じる」・背景のタップで閉じる。
- 開いたときは、ホームで開いている日が選ばれ、その月が出る。「今日」ボタンで、今の月・今日の選択に戻る。**未来の日は選べない**。今の月より先へは進めない。記録のある日に点が付く。今日は枠、選んだ日は塗りつぶし。
- **ホームの「今日に戻る」ボタンは今のまま**（日付の下。日付の文字を押す＝カレンダー、「今日に戻る」＝今日へ、で押す場所が別なので両立する）。
- **履歴タブのカレンダー（`calMonth`／`renderCalendarHtml`）とは別の状態**。月の移動などは互いに影響しない。見た目の部品（`.cal-table`・`.cal-dot`・`.cal-hdr`、`.history-entry`）は共用。
- 記録の表示（`entryText`）は、選んだ値・カロリー・金額・時間・距離・歩数・体重・体脂肪を「 · 」でつなぎ、何も無ければメモ、それも無ければ「記録あり」。ホームのカード・履歴タブの一覧は、それぞれ独自の整形のままで、この関数には置き換えていない。

## 手放し候補（服の管理）
- 服の管理の「手放し候補（N）」ボタンから開くダイアログ（`wdCand*`関数）。**しばらく着ていない服を、着ていない期間が長い順に並べ、「手放す」か「残す」を1タップで選ぶ**（着ない服を処分するきっかけ）。集計は**`LifeLogLogic.discardCandidates`**（DOMに触れない）。
- **対象は現役の服のうち、「出さない」服（残すと決めた服）と手放した服を除いたもの。既定は今の季節（と通年）の服だけ**（冬に夏の服を「着ていない」と言わないため。4・5・10月は季節の絞り込みなし）。「すべての季節」に切り替えられる（季節の切り替えは、季節の絞り込みがある月だけ出す）。
- **着ていない期間**＝最後に着た日から今日まで。**一度も着ていない服は、そのカテゴリの記録の最初の日から今日まで**（記録を始めたばかりの頃に、全部が候補にならないように。「記録を始めてから◯日」と出す）。記録が1件も無いカテゴリは判断できないので候補を出さない。今日より後の日の記録は使わない。
- **日数のしきい値は30／60／90／180日以上（既定60日）**。ボタンに、それぞれの件数を出す。同じ期間なら、一度も着ていない服が先、次に一覧の並び順。
- 行には、着ていない日数（大きく）・名前・ブランドの略称・グループ・種類・季節・着数・最後に着た日・全期間の着用回数を出す。
- **「手放す」**＝`{r:true, z:false}`（記録と統計は残し、記録画面から隠す）。**「残す」**＝`{r:false, z:true}`（持ち続けるが、上の列・提案・この一覧には出さない。礼服・部屋着など）。どちらも`WD_STATUS`＋`wdMutate`を通す（元に戻せる。保存できなければ取り消して知らせる）。操作後は一覧と、後ろの画面のボタンの件数を更新する。**条件（日数・季節）を切り替えたときも、ボタンの件数を同じ条件で数え直す**（`wdCandRefreshBtn`。閉じたあと・開き直したあとに、一覧とボタンの数字がずれないように）。

## トースト（`#toast`）
- 長い文は折り返す（`width: max-content`と`max-width`で画面内に収める。`white-space: nowrap`にしない。以前は`left: 50%`のせいで利用できる幅が半分になり、長い通知が切れていた）。通知文は1〜2行に収まる長さにする。

## 変更時の注意
- ロジック（集計・移行・重複排除など）は`logic.js`に切り出してテストを書く。DOM描画と切り離せる部分を`index.html`に直接書かない。
- 保存済みデータの形を変える場合は、起動時とインポート時の両方で移行・修復を通す（`repairLogs`の呼び出し箇所を参照）。
- テスト追加時は、対象コードを一時的に無効化してテストが落ちることを確認する（偽陽性防止）。

## 開発予定（コーデの整理）
服が増えて選択画面が長くなったことへの対応。この順で進める：
1. 不具合修正（重複記録）— 完了
2. データモデル拡張と「服の管理」画面 → 利用者がPCで既存データを棚卸し
   - 2-a. ロジックとテストのみ（`logic.js`。画面の変更なし）— 完了
   - 2-b. 「服の管理」画面（設定タブの中。スマホは縦のカード、PC幅は表形式。名前変更・統合・一括設定・元に戻す）。選択画面では手放した服を隠す（ただしその日に記録済みの服は残す）— 完了
3. 記録画面とグループ別の統計
   - 3-a. 記録画面（グループ・種類の見出し、季節の切り替え、最近着た服、検索、その場で追加）— 完了
   - 3-b. グループ別の統計（期間の切り替え、手放した服の表示、1着あたりの回数）— 完了

4. 着ていない服を上に出す・手放し候補（バランスよく着る／着ない服を処分するきっかけ）
   - 4-a. 「提案に出さない」の目印（`meta.z`）、記録画面の上の列（着ていない順・回数が少ない順・最近着た順）— 完了
   - 4-b. 服の管理に「手放し候補」の一覧（一定期間着ていない服を、着ていない期間つきで並べ、「手放す」か「残す」を1タップで選ぶ）— 完了
   - 4-c. 分類を使わないすべてのカテゴリ（時計・靴・食事など、新しいカテゴリも）の記録画面に、並び替え（登録順／着ていない順／回数が少ない順）— 完了

設計の結論：
- **グループ（トップス／ボトムス／アウター）＋種類（長袖T・パーカー・ジャケット等の任意の小見出し）の2段**。グループは部位、種類は品目。両方とも利用者が追加できる。
- 項目は`{名前, グループ, 種類, 季節（夏/冬/通年）, 着数, 状態（現役/出さない/手放した）}`を持つ。季節の初期値は名前のキーワードから推定する（着用月からは推定しない。記録期間が1シーズン分しかないため）。
- **手放した服は選択画面から隠すだけで、`logs`・統計には残す**（着回しの統計が目的のため）。バリエーション率とおすすめの対象からは外す。
- 同じような服を複数持つ場合は1項目のまま「着数」で表し、統計では1着あたりの回数も出す。
- 統計はグループごとに分けて出す（Tシャツとパンツを同じランキングに混ぜない）。集計期間は切り替えられ（30日／90日／半年／1年／全期間）、**初期値は全期間**。画面に集計期間を必ず表示する（以前のインサイトは直近90日固定で表示が無く、全期間の数字に見えた。3-bで解消）。
- 時計・ネックレス・シューズなど数の少ないカテゴリは、分類を始めず平らな一覧のまま使う。分類を使うかどうかはカテゴリごとに選ぶ。
- 棚卸しの操作は、直前の状態を自動で保存して「元に戻す」を付ける（取り込みが全データの上書きで、操作が連続するため）。
